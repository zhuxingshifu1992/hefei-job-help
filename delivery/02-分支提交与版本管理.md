# 02 · 分支策略 / 提交规范 / 版本与 Tag 管理

---

## 1. 分支策略

### 1.1 现行策略：单分支 `main`

本项目单人维护、无并行开发、无构建流程，**刻意不使用 develop/feature/release 分支**。

| 场景 | 做法 |
|---|---|
| 日常资讯更新 | 直接在 `main` 提交并推送 |
| 新增脚本/改配置 | 直接在 `main`，但**先本地验证通过**再提交 |
| 颠覆性改动（换数据源、重构前端） | 开临时分支，验证后再合回 `main` |

### 1.2 什么时候才需要开分支

仅在「改坏了会立刻影响线上访客」时：

```bash
# 开分支
git checkout -b refactor/store-js

# …改动、本地验证…

# 合回 main
git checkout main
git merge refactor/store-js
git branch -d refactor/store-js
```

> 因为 push `main` 就等于发布（Pages 自动部署），**在 `main` 上提交等于上线**，这是本策略唯一需要注意的风险点。

### 1.3 分支保护（可选，GUI）

路径：**Settings → Branches → Add branch ruleset**，对 `main` 勾选：
- Require a pull request before merging（若有多人协作）
- 本项目单人维护时**不建议开启**，会拖慢日常更新

## 2. Commit Message 规范

### 2.1 格式

```
<类型>: <中文简述>（不超过 50 字）

<可选正文：为什么改、影响面>
```

**类型取值**（只用这 6 个，够用且不易乱）：

| 类型 | 用途 | 示例 |
|---|---|---|
| `feat` | 新增功能或新增数据能力 | `feat: 资讯页增加「已入驻」筛选` |
| `fix` | 修复缺陷 | `fix: 修复腾讯文档取票404(自动选最高版本插件目录)` |
| `data` | 纯数据变更（增删改资讯） | `data: 巡检新增2家(优享陪诊/智联招聘)，共63条` |
| `docs` | 文档/交付包变更 | `docs: 新增 GitHub 运维交付包` |
| `chore` | 脚本、配置、时间戳刷新等杂项 | `chore: 每日资讯自动更新 [条目=63]` |
| `refactor` | 重构，不改变外部行为 | `refactor: store.js 抽离计划默认值` |

### 2.2 本仓库历史风格（兼容参考）

已有提交示例：

```
data:   巡检新增2家(优享陪诊/智联招聘)+更新妙小医招聘动态,共63条(2026-09-10)
fix:    修复腾讯文档取票404(自动选最高版本插件目录) + 刷新资讯时间戳(2026-09-10)
chore:  proactive peizhen research
docs:   计划重置为9/10起60天冲刺(23任务,基于63条最新资讯)
```

**约定**：新提交统一加类型前缀；历史提交不强求回溯改写。

### 2.3 一条好提交信息的自检

- [ ] 能看出**改了什么**（数据条数 / 文件名 / 功能点）
- [ ] 数据类提交写明了**条数与日期**，如 `共63条(2026-09-10)`
- [ ] 修复类提交写明了**根因而非现象**（`取票404` 优于 `拉取失败`）
- [ ] 不含密钥、token、绝对路径中的敏感信息

### 2.4 提交前必做检查

```bash
cd /d/帮老弟找工作项目
git status --short          # 确认没有多余文件被带上
git diff --stat             # 确认改动范围
# 重点：确认 tools/.gh_token 不在待提交列表里
git status --porcelain | grep gh_token && echo "⚠️ 危险：token 将被提交" || echo "OK：token 未入库"
```

## 3. 版本与 Tag 管理

### 3.1 现状

**当前仓库 tag 数为 0**。本项目此前只按日期推进，未做版本标记。建议从现在起建立以下规范。

### 3.2 命名：`v<主>.<次>.<补丁>`

| 变更类型 | 版本位 | 示例 |
|---|---|---|
| 结构性变更（换数据源、改仓库约定、重构前端） | 主版本 | `v1.0.0` → `v2.0.0` |
| 新增能力（新脚本、新页面、自动化上线） | 次版本 | `v1.0.0` → `v1.1.0` |
| 数据更新、文案修正、小修复 | 补丁 | `v1.1.0` → `v1.1.1` |

### 3.3 打 tag 的时机

**只在这三种时刻打**，不要每条数据更新都打：

1. 计划整体重置（如 `p60` → `p0910`）
2. 工具链/流程变更（如修复取票 404、新增同步脚本）
3. 里程碑（资讯突破 50/100 条、自动化上线）

### 3.4 操作命令

```bash
cd /d/帮老弟找工作项目

# ① 轻量 tag（推荐，够用）
git tag -a v1.0.0 -m "v1.0.0 计划重置为9/10起60天冲刺；资讯63条；修复腾讯文档取票404"

# ② 查看
git tag -l
git show v1.0.0 --stat

# ③ 推送 tag（token 方式，推完恢复 remote）
TOKEN=$(tr -d '[:space:]' < tools/.gh_token)
git push "https://${TOKEN}@github.com/zhuxingshifu1992/hefei-job-help.git" v1.0.0
git remote set-url origin https://github.com/zhuxingshifu1992/hefei-job-help.git

# ④ 删除本地/远端 tag（打错时）
git tag -d v1.0.0
git push "https://${TOKEN}@github.com/zhuxingshifu1992/hefei-job-help.git" --delete v1.0.0
```

### 3.5 用 tag 做回滚（比 `git revert` 更直观的场景）

```bash
# 查看某个 tag 时的数据条数（不改动工作区）
git show v1.0.0:data/info.json > /tmp/old_info.json
python -c "import json;print(len(json.load(open('/tmp/old_info.json',encoding='utf-8'))['items']))"

# 确认要回滚：把某文件恢复到 tag 状态
git checkout v1.0.0 -- data/_source.json
git commit -m "fix: 回滚 _source.json 至 v1.0.0"
```

## 4. 撤销与回滚速查

| 场景 | 命令 | 风险 |
|---|---|---|
| 撤销未提交的改动（**危险，会丢改动**） | `git checkout -- <文件>` | 改动不可恢复 |
| 把文件移出暂存区（保留改动） | `git restore --staged <文件>` | 安全 |
| 撤回最近一次提交但保留改动 | `git reset --soft HEAD~1` | 安全 |
| 线上已发布，要撤回某次提交 | `git revert <commit>` 然后 push | 安全，推荐 |
| 强制回退到某 commit（**危险**） | `git reset --hard <commit>` | 会丢失之后的提交，禁用于已推送内容 |

> **本项目铁律**：已经 push 到 `main` 的内容，一律用 `git revert`，**禁止 `git reset --hard` + 强推**。
