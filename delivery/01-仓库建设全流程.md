> 面向「从零复刻」的场景。若仓库已存在，跳到 §2 核对目录规范即可。

## 1. 仓库规划与初始化

### 1.1 建仓前的四个决定（本项目实际选择）

| 决策项 | 本项目选择 | 原因 / 复刻时注意 |
|---|---|---|
| 仓库可见性 | **Public** | GitHub Pages 免费版要求公开仓库（私有仓库需付费套餐）。若内容敏感，改用私有仓库+其他托管 |
| 分支模型 | **单分支 `main`** | 单人维护、无并行开发，多分支只增负担 |
| 技术栈 | **纯静态**（HTML/CSS/JS，零构建） | 不需要 npm install、不需要 CI，改完直接 push 即生效 |
| 部署方式 | **GitHub Pages（分支部署）** | push 到 `main` 自动触发，约 40~60 秒生效；无 GitHub Actions |

### 1.2 从零初始化（照抄即可）

```bash
# ① 进入项目目录
cd /d/帮老弟找工作项目

# ② 初始化仓库
git init

# ③ 配置身份（只影响本机提交署名）
git config user.name  "你的名字"
git config user.email "你的邮箱@example.com"

# ④ 关键：统一换行符处理，避免 Windows/Linux 混用导致全量 diff
git config core.autocrlf input

# ⑤ 先建 .gitignore，再 add（否则 token 会被提交上去）
#    内容见 06-配置模板与脚本/.gitignore.template

# ⑥ 首次提交
git add .
git commit -m "chore: 初始化项目"

# ⑦ 关联远端（用默认分支名 main）
git branch -M main
git remote add origin https://github.com/zhuxingshifu1992/hefei-job-help.git
```

**首次推送（需要 token，见 `03-权限与安全配置.md`）**：

```bash
TOKEN=$(tr -d '[:space:]' < tools/.gh_token)
git push "https://${TOKEN}@github.com/zhuxingshifu1992/hefei-job-help.git" main
# 推完立刻把 remote 恢复成干净地址，避免 token 留在配置里
git remote set-url origin https://github.com/zhuxingshifu1992/hefei-job-help.git
```

> 若仓库在 GitHub 上已存在且非空（如有 README/LICENSE），先 `git pull --rebase origin main` 再推。

### 1.3 开启 GitHub Pages（GUI 操作，需人工点击）

路径：**仓库页面 → Settings → Pages → Build and deployment**

- Source 选 **Deploy from a branch**
- Branch 选 **main**，目录选 **/ (root)**
- 点 Save，等待 1 分钟

验证：

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://zhuxingshifu1992.github.io/hefei-job-help/index.html
# 期望输出 200
```

> 站点根路径是 `https://<用户名>.github.io/<仓库名>/`。**页面内所有资源引用必须用相对路径**（如 `assets/css/base.css`），写成 `/assets/...` 会因路径前缀而 404。

### 2.2 目录职责边界（改动前先确认放对地方）

| 目录 | 谁能改 | 说明 |
|---|---|---|
| `data/_source.json` | 脚本 / AI 经 `edit_source.py` | **权威源**，所有资讯变更的入口 |
| `data/info.json` | **只能由 `gen-info.js` 生成** | 手改会被下次生成覆盖 |
| `data/*.js` | 原则上不动 | 仅作为无网络时的回退数据源 |
| `assets/js/store.js` | 改默认计划时才动 | 内含 `defaultPlan()`，决定新访客看到的计划 |
| `tools/` | 运维变更时 | 每个脚本头部都有中文说明，改前先读头部注释 |
| `memory/` | AI 收尾时更新 | 决策、进度、交接，供下一个 agent 接手 |
| `delivery/` | 流程变更时 | 本交付包 |

### 2.3 命名规范

**文件命名**
- 脚本/数据文件：小写 + 下划线（`fetch_tdoc.py`、`gen-info.js`）——历史文件保留原名，新文件统一用下划线
- 文档：中文命名可读优先（`求职计划.md`、`项目结构规划.md`）
- 生成产物加下划线前缀以示「非手改」：`_source.json`

**数据条目 `id`**（`_source.json` 内每条资讯）
- 规则：小写拼音/英文缩写，无空格无中文，如 `yueban`、`zanduoduo`、`8hao`
- 同一平台**只能有一个 id**，新增前必须 `edit_source.py list` 去重
- 禁止复用已删除条目的 id（避免缓存/引用混乱）

**提交信息**：见 `02-分支提交与版本管理.md`

## 3. README 与文档编写规范

### 3.1 仓库根 README 应包含的六段

本项目根 README 可用下面模板（若已有，按此结构校准）：

```markdown
# 项目名

一句话说明：给谁、解决什么问题。

## 在线访问
https://<用户名>.github.io/<仓库名>/

## 能看什么
- 首页：今天要处理的事
- 资讯页：可接单平台 / 本地招聘（共 N 条，更新于 YYYY-MM-DD）
- 计划页：分阶段求职任务（数据存在浏览器本地）

## 数据来源
腾讯文档表格（人类可编辑）↔ 本地 data/_source.json（权威源）

## 本地运行
无需构建，双击 index.html 即可；或 python -m http.server 8123

## 维护
见 delivery/ 交付包
```

### 3.2 文档编写通用规范

1. **先写「为什么」再写「怎么做」**——`memory/decisionLog.md` 每条决定都必须记录原因与被否决方案。
2. **数字要可验证**：写「63 条」而不是「很多条」；写「约 40~60 秒」而不是「稍等」。
3. **命令必须是能直接粘贴的整行**，含完整绝对路径；不写 `$ python script.py` 这种需要先 cd 的省略形式，或在命令首行补 `cd`。
4. **涉及删除/覆盖/推送到公开仓库的操作**，必须写明风险与回滚方式。
5. **文档层级**：一个主题一个文件，用 `NN-主题.md` 编号，README 只做导航不堆细节。
6. **改动即更新**：流程一变，同步改文档，并在 `memory/decisionLog.md` 追加一条决定。

### 3.3 文档与代码的一致性检查

每次运维收尾前跑一遍：

```bash
cd /d/帮老弟找工作项目
# 确认文档中写的条数与实际一致
python -c "import json;print('实际条数:',len(json.load(open('data/info.json',encoding='utf-8'))['items']))"
```

若 `delivery/README.md` 或 `求职计划.md` 里的条数与此不符，一并修正后再提交。
